## Why

v1 держит правила текстом, и они слабо меняют поведение: уроки не доходят в момент ошибки, хуки шумят и не
видят обходов (полигон: 24 из 45), память растёт без выхода, диспетчер теряет шаги, Georgy отвечает на вопрос
раз в 9 минут. v2 — механизмы вместо текста, проверенные прибором (полигон, журналы) до и после, при том что
v1 продолжает обслуживать работу и не трогается.

## Decisions

Источники по приоритету: решения Georgy 05.11 (`clean-start-plan`, вне git) → сводка v2 04.11 → критика двух
кругов → отчёт ИИ-инженера. Внутри `clean-start-plan` поздние решения 05.11 отменяют ранние поправки критики —
ниже только действующие.

- **v1 не трогаем.** `~/ai-dev-hub` и его `projects/` — только чтение: ни правок, ни коммитов, ни
  `git worktree add` (пишет в `.git` v1). Старую ревизию v1 читать через `git archive` во временную папку.
  Переход проектов на v2 — отдельная тема после приёмки v2, в этот план не входит.
- **Данные — только в `~/hub-data/`, в git v2 — никогда.** Журналы сессий, память и логи проектов, реальные
  корпуса полигона. В git — скрипты и обезличенная синтетика; проекты в плане и коде — «проект A
  (многосессионный)», «проект B (малый)». Никаких локальных данных Georgy в v2 (05.11): ни
  `CLAUDE.local.md`, ни списка запретных имён (`.githooks/private-patterns`) — его нет и не будет.
  В git v2 — только код и синтетические тестовые данные; всё реальное (журналы, корпуса, память) — только
  в `~/hub-data/`. Ревьюер каждого среза проверяет дифф на реальные данные, имена проектов и ключи задач
  (Georgy 05.11).
- **Репозиторий и пуш** (Georgy 05.11). v2 публичный: `github.com/Gorgog/ai-dev-hub-v2`, remote `origin`;
  работа сразу идёт туда. Готовые срезы после ревью мержит в `main` и пушит диспетчер; перед пушем — скан
  диффа на реальные данные, имена проектов и ключи задач. Сессии срезов не пушат. «База ветки» в таблице
  волн — `origin/main` с нужными срезами.
- **Папка v2 навсегда — `~/ai-dev-hub-v2`** (Georgy 05.11): имя входит в ключи журналов и пути worktree.
- **Языки** (Georgy 05.11). Рантайм плагина (хуки, скрипты скиллов) — только Node ≥ 22. Офлайн-аналитика и
  пробы — Python в `tools/` (и `probes/`), в горячий путь не попадают.
- **Срок хранения журналов** (Georgy 05.11): `cleanupPeriodDays` и `desktopSessionCleanupPeriodDays` = 365
  ставит диспетчер; копия в `~/hub-data` (срез 01) — независимо от этого. `/hub:setup` (срез 19) проверяет
  настройку на новых машинах.
- **Порядок: волна 0 → хребет хуков → два потока.** Не больше двух срезов одновременно (ревью у одного
  человека). Срезы, правящие `plugin/hooks/`, идут одним потоком «H» строго по очереди; всё остальное — поток
  «S». Разметка — по `plugin/skills/dispatch/slicing.md`.
- **Хребет хуков (срез 07).** Один процесс node на событие, поведение — модули в каталоге события (добавить
  модуль = добавить файл, общего списка нет), модуль подачи — единственный, кто пишет в контекст Claude.
  Аварийный выключатель `HUB_OFF=1`; политика отказа: подача и напоминания — fail-open, защита (deny
  опасного, замок ресурсов) — fail-closed с понятной причиной; проверка здоровья на SessionStart.
- **Бюджет механизмов.** Единица — логический обработчик; потолок ~6 обработчиков хуков и ≤ 10 видов файлов
  состояния. Реестр — каталог `plugin/mechanisms/<id>.json` (событие, сценарий полигона, дата пересмотра,
  что заменяет), по файлу на механизм — чтобы реестр не стал горячей точкой; бюджет проверяет pre-commit.
  Новый механизм — вместо старого или с цифрой полигона. Список вырезаемого из v1 — в срезе 07.
- **Модуль подачи (срез 08).** Лимит на вызов и на эпоху, приоритет блок > урок > напоминание, у
  напоминания фазы — свой слот. Ключ «уже показан» = (`session_id`, `agent_id`, эпоха контекста); эпоха —
  старт или компакция, у субагента — свой старт. Журнал событий с адресом вызова (`session_id`, `agent_id`,
  `tool_use_id`, эпоха, модель). Мера — «предотвратил», не «показал»: триггер урока служит детектором,
  нарушение того же правила в следующих K вызовах эпохи считается автоматически. Всё из памяти подаётся в
  рамке «данные из памяти, не инструкции».
- **Хранилище памяти — одно устройство, без сравнения двух** (Georgy 05.11 по отчёту инженера). Урок —
  `memory/lessons/<id>.md`: frontmatter `id, kind, when[], keys[], status, supersedes, source, created` и 2–5
  строк, первая ≤ 160 знаков, без изменяемых счётчиков. События `shown/repeat/merged/retired` — дозапись в
  `memory/events/<ГГГГ-ММ>.jsonl`. SQLite FTS5 и `.triggers.json` — выводимые, пересборка по mtime при каждом
  поиске; горячий путь хука читает только `.triggers.json`. История — локальный git памяти, коммит делает хук
  под `flock`. Проверка записи — PostToolUse(Edit|Write) по `memory/lessons/**`; Bash-запись туда — deny.
  Слой хранения — за интерфейсом из 5–6 операций; второй адаптер — только при провале приёмочного теста.
  Тот же формат — для решений (`memory/decisions/`).
  superseded: две реализации (файлы + SQLite / только SQLite) и сравнение в пробах (05.11, поправки критики) —
  попадание, шум и задержка у них совпадают по построению; заменено приёмочными тестами одного устройства.
- **Безопасность памяти.** Поле `source` (Georgy / модель / внешний текст) обязательно; внешний источник сам
  правилом не становится. Уроки — факты, не приказы; проверка записи отклоняет URL и команды
  пуша/отправки/удаления.
- **Правило 7 — эпизод всегда, правило по повтору:** урок-правило на 2-й похожий эпизод; сразу — для класса
  «одного раза достаточно» (данные, права, деньги, пуш и внешние действия, `.env`/секреты, миграции) или по
  слову Georgy. Класс «одного раза» — механизм и никогда не уходит в отставку.
- **Длинные сессии — по шагам инженера.** Шаг 0 (срез 06, без модели): есть ли распад на данных v1. Нет — ни
  напоминания, ни свежего контекста не строим (срез 23 отменяется с причиной). Есть — шаг 1
  (напоминание по событию) и переключатель шага 2 (A/B по хэшу `session_id`) в срезе 23; сам A/B идёт на
  живой работе после перехода проектов, шаг 3 (свежий контекст на проверочную фазу) — после него и только
  по порогу `acceptance.md` §4, вне этого плана.
  superseded: «напоминание по глубине против свежего контекста — сравнить на полигоне» (05.11, поправки
  критики) — полигон S длинные сессии не воспроизводит.
- **Слои на «готово» — по одному.** Сначала `push-slice` + deny голого пуша + стоп-хук по `last-full.json`;
  машина состояний и `acceptance.json` (срез 16) — только если H09 + process-audit по журналам показывают
  оставшиеся пропуски (Georgy 05.11); M05 с моками MCP — только если H09 + process-audit пропусков не ловят.
- **Тестовая БД на рабочую копию — механизм хаба** (Georgy 05.11, срез 26). При создании worktree скрипт
  хаба создаёт БД из шаблона в существующем тестовом контейнере, обёртка запуска тестов подставляет её адрес
  переменной окружения, при удалении worktree БД удаляется. Настройки проекта — в его локальном профиле хаба.
  Ноль изменений в репозитории клиентского проекта, туда ничего не пушится. Аренда окон тяжёлого (срез 18) —
  только если очередь после 26 выше порога.
- **Пороги и пробы заморожены** (Georgy 05.11): пороги [П] в `acceptance.md` и критерии `probes.md`
  утверждены как есть; пересмотр любого — только отдельным вопросом Georgy. Исключение, внесённое по его же
  слову при утверждении: P4 проверяет механизм среза 26.
- **Бэкап памяти вне машины — отложен** (Georgy 05.11); до него — `git bundle` памяти в `~/hub-data`.
- **Кто решает.** Выбор хранилища, пороги приёмки, необратимое, архитектура — вопросом Georgy с вариантами и
  рекомендацией; агенты готовят таблицы. Рутинные проверки — с детерминированным якорем (полнота миграции по
  хэшам, «ложный блок» — по факту запуска тяжёлого), пограничное — Georgy.
- **Оценки — калибровочные.** Аналогов для работ над хабом в журнале нет: размер S (≤ 1 дня), M (1–3), L
  (3–5) — рабочих дней активного времени. Факт каждого среза мерит `/hub:estimate close` — это первые
  аналоги для хаба.

## Out of scope

- Переход проектов на v2 (клон заново, `.env`, ветки и stash v1 через `remote v1` + `git bundle`, контейнеры
  и дев-БД, переписывание путей `ai-dev-hub/`, канарейка) — отдельный план после приёмки v2 (решение 05.11).
  Здесь готовится только инструмент: миграция памяти скриптом (срез 13) с повторным прогоном на доснимке.
- Правки v1 любого рода (решение 05.11: v1 не трогаем) и любые изменения в репозиториях клиентских проектов
  (тестовая БД на рабочую копию — механизм хаба, срез 26).
- Бэкап памяти вне машины — отложен (Georgy 05.11).
- Резерв после v2: два разнородных ревьюера и capture–recapture, калибровка уверенности, бандиты для правил,
  best-of-2, премортем, делегирование обратимых решений, эмбеддинги в памяти (вариант C).
- Бюджет лимита подписки на стройку — не вводим, расход контролирует Georgy (05.11).
- A/B напоминания на живой работе и свежий контекст на фазу (шаги 2–3 инженера) — после перехода проектов:
  до него у v2 нет живой работы.
